# Agent & Developer Workflow Analysis
## Insights from `tmp-codex-onboarding.txt`

### 1. Agent Onboarding & Project Discovery
**Observation:** An effective initial agent workflow is to list files, read `package.json` for scripts, and run a lint/check command to establish a baseline. This verifies the environment and core tooling.
**Recommendation:** Standardize this as the first step for any agent working on the project. Document this in the main `README.md` or `AGENTS.md`.

### 2. Critical Project-Specific Commands & Conventions
**Observation:** The default `git status` is misleading. The command `git status --untracked-files=all` is essential for an accurate view of the working directory. This was a critical correction from the human.
**Recommendation:** This command should be aliased or documented prominently for all developers (human and AI). The agent-specific documentation (`GEMINI.md`, `CLAUDE.md`) should mandate its use over the standard `git status`.

### 3. Task Decomposition & Management
**Observation:** The agent (Claude) initially tried to create a single, massive todo list for a repetitive task (reviewing 36 files), which was unmanageable. The human guided it to a cyclical, one-item-at-a-time process.
**Recommendation:** For large, repetitive tasks, prompts should explicitly instruct the agent to work on items sequentially, completing all steps for one item before starting the next. This avoids overwhelming the context window and makes the process more robust.

### 4. The Danger of Incomplete Analysis
**Observation:** The agent made a critical error trying to use the `exec` command. It searched for the keyword but failed to read the entire source file, leading to a complete misunderstanding of its usage. The user noted: "Partial reading...leads to absurd behavior".
**Recommendation:** Agents must be explicitly prompted to read the *entire* relevant source file(s) before attempting to use a new function or command. A "best practice" of full-file-read over keyword search should be enforced.

### 5. Test Quality and Philosophy
**Observation:** The agent initially wrote weak tests using `contains:`. The user forced a much higher standard, requiring exact output verification. Crucially, when the agent tried to commit a "fake test" (testing only error paths), the user immediately rejected it as unacceptable.
**Recommendation:** The project must have a documented testing standard that mandates: 1. Testing the primary success path. 2. Using exact output assertions over partial/`contains` checks where possible. 3. Verifying exit codes. This philosophy should be part of the P0001 roadmap/documentation.

### 6. Learning from Examples
**Observation:** The agent finally solved the complex `$arg` test by abandoning its flawed analysis and instead reading existing, working test files (`$defmacro.yaml`, `$macro.yaml`) to learn the correct invocation pattern.
**Recommendation:** When an agent is stuck, a powerful heuristic is to prompt it to find and learn from existing, high-quality examples of similar code within the project. This is often more effective than trying to reason from first principles with incomplete information.

### 7. Handling the Development Environment
**Observation:** The agent repeatedly failed pre-commit hooks (`lefthook`) and forgot to stage files after running formatters (`pnpm run fix`).
**Recommendation:** The standard agent workflow before any commit must be: 1. Run `pnpm run fix`. 2. `git add .` (or specific files). 3. `git commit`. This checklist prevents trivial rejections by the CI/hooks.

### 8. Codifying Knowledge
**Observation:** The user immediately had the agent document newly established procedures (the 8-step review, the `git status` rule) in the project documentation.
**Recommendation:** This "living documentation" approach is highly valuable. All developers and agents should be encouraged to make small, immediate documentation commits as soon as a process improvement is discovered.
